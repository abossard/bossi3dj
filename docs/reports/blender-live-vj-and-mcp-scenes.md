# Play Blender as a pre-built instrument

The best way to use Blender 5.2 LTS live on an Apple Silicon Mac is as a single pre-compiled, parameterized scene that runs in a visible Blender window, takes a handful of control values over one OSC port, and publishes a 1080p30 (or 720p) camera feed over Syphon into the VJ host. It is not a clip mixer and not a low-latency reactive engine. The ceiling is set by Blender's single main thread, which has to drain input, evaluate the scene, draw the viewport and read the frame back to the CPU, all within one frame budget. On an M1 Max, offscreen EEVEE capture alone measured about **40 fps at 1080p for the default cube**. The biggest live hazard is EEVEE shader compilation on first draw, which Metal can neither parallelize nor avoid, so every look has to be warmed up before the show. For authoring, an LLM agent works best through the official Blender Lab MCP server, using one general "execute Python" tool, a template scene with a single control datablock, short idempotent build scripts kept in version control, and a screenshot after every step. Agents handle layout, Principled materials, lights and cameras well, and they consistently fail at debugging non-trivial Geometry Nodes graphs. No published case study shows an MCP-built Blender scene used live, so the workflow below is assembled from components that each work, not from a proven end-to-end recipe.

## Blender earns a live slot only as a fixed scene with a few driven parameters

Every credible source describes live Blender the same way. You get a tightly authored scene with a few external controls, not a library of clips. The OK Go "Impulse Purchase" project was built almost entirely in Geometry Nodes and supported **real-time interactivity through OSC inputs**, including facial mocap ([BCon 2025](https://conference.blender.org/2025/presentations/4081/)). A theatre project drives real-time playback from motor rotation speed ([BCon 2026](https://conference.blender.org/2026/presentations/4160/)), and the 2026 viewport talk pitches shaders, the viewport compositor and Geometry Nodes as production-grade real-time tools ([BCon 2026](https://conference.blender.org/2026/presentations/4185/)). None of these sources publishes frame rates, hardware or crash data. The negative evidence is older and specific. In a 2022 thread one VJ gave up on EEVEE for TouchDesigner, another called live Blender "absolutely not practical", and a working video DJ described his pre-rendered Blender clips as "static but very reliable" ([BlenderArtists](https://blenderartists.org/t/is-anyone-using-blender-as-a-vj-tool/1387361)). That verdict predates EEVEE Next and the 5.x instancing work, but its core complaints still hold. Subdivision, armatures and particles are CPU-bound per frame, and the Blender editor is far heavier than a game engine.

The 5.x releases favour exactly the live-friendly path. EEVEE in 5.2 makes **instancing-heavy scenes up to twice as fast**, removes the limit of 8 object attributes per material, adds larger shadow pools, and makes Fast GI cheaper. It also re-renders every frame during playback even when nothing changes, so idle accumulation can't be counted on ([5.2 EEVEE notes](https://developer.blender.org/docs/release_notes/5.2/eevee/)). Workbench and Overlay instancing in 5.0 reach **up to 3x higher fps** with many instances ([5.0 EEVEE notes](https://developer.blender.org/docs/release_notes/5.0/eevee/)). The practical content recipe follows from this. Use Geometry Nodes instancing in place of particles, displacement and normal maps in place of subdivision, and per-instance attributes feeding shader inputs, with a few scalars moving everything. The settings that cost frames are known from the EEVEE Next migration. Jittered soft shadows are off in the viewport by default "because of their cost", and too fine a shadow Resolution Limit causes "a large performance penalty" ([4.2 migration](https://developer.blender.org/docs/release_notes/4.2/eevee_migration/)). Bloom now lives in the compositor as Glare in Bloom mode, which is much faster than Fog Glow, while Fog Glow still runs on a slow CPU path in the viewport compositor ([4.2 compositor notes](https://developer.blender.org/docs/release_notes/4.2/compositor/)). Files authored in 4.x to 5.1 need a look check under 5.2, because its Screen Space Raytracing rework changes how scenes look ([5.2 EEVEE notes](https://developer.blender.org/docs/release_notes/5.2/eevee/)).

Shader compilation is the stutter that matters most. A tester measured **27 s for EEVEE Next's general shaders versus 2 s in legacy EEVEE** on a cold cache ([devtalk](https://devtalk.blender.org/t/blender-4-2-eevee-next-feedback/31813?page=21)). Editing a Mix node value has caused 2 to 4 s recompiles ([Issue #120586](https://projects.blender.org/blender/blender/issues/120586)), which means some node inputs you drive live can trigger a recompile rather than a cheap uniform update. On macOS the Thread/Subprocess compilation options are unavailable ([Manual, System prefs](https://docs.blender.org/manual/en/latest/editors/preferences/system.html)). Blender 5.1 cut cold Metal compile time by 33% but made the warm, cached case **130% slower** (1.18 s to 2.72 s on an M1 Ultra), with a fix promised for the next release ([5.1 EEVEE notes](https://developer.blender.org/docs/release_notes/5.1/eevee/)). The 5.2 notes don't mention that fix, so treat it as unresolved. The consequence is a rule, not a tuning tip. Every material and every scene has to be drawn once at show resolution before doors open, and you can't add new material combinations during the set.

Audio reactivity is the weakest native piece. Blender itself only bakes a sound file's amplitude to F-curves ([manual](https://docs.blender.org/manual/en/2.92/editors/graph_editor/fcurves/editing.html)). Live analysis needs add-ons. A2B is the only one that states support for both Blender 5.1+ and macOS ARM64, and it writes FFT bands, onset and experimental BPM to mesh attributes for Geometry Nodes ([A2B docs](https://superhivemarket.com/products/a2b-51/docs)). AudVis stops at Blender 5.0 ([Superhive](https://superhivemarket.com/products/audvis)), and Audio Nodes has no published macOS build information ([BCon 2026](https://conference.blender.org/2026/presentations/4157/)). None of them publishes latency figures. My recommendation for a setup with a dedicated host like SwiftVJ is to run the audio analysis in the host and send Blender a few normalized scalars over OSC. That keeps Blender's input surface to one path. This is a design inference, not a measured comparison.

Against the alternatives, Blender sits in a narrow but real niche on this hardware. Practitioner and vendor sources cast Blender as the asset tool and TouchDesigner, Notch or Unreal as the live engines ([Interactive & Immersive HQ](https://interactiveimmersive.io/blog/deployment/creating-dj-visuals-with-touchdesigner/), [Notch NGHTMRE](https://www.notch.one/madewithnotch/nghtmre)). On an M1 Max, Notch and the Unreal live-events stack are largely off the table, a point drawn from background knowledge that the notes did not verify. That leaves TouchDesigner and Blender itself, and it makes Blender's procedural Geometry Nodes content and EEVEE look worth the engineering effort for a few hero scenes, backed by pre-rendered clips for everything else.

## One main-thread timer carries control in and frames out

Every input path into Blender ends on the main thread, because Python threads that touch `bpy` "cause Blender to crash in hard to diagnose ways" ([API gotchas](https://docs.blender.org/api/current/info_gotchas_threading.html)). Every maintained add-on uses the same pattern. A receive thread fills a buffer, and a `bpy.app.timers` callback applies the values. The table shows where each protocol stands for 5.x.

| Path | Best 5.x option | Status and limits |
|---|---|---|
| OSC | Custom extension polling a non-blocking UDP socket from a timer | NodeOSC released v2.4.4 in 2026 but ships no extension manifest and states no 5.x support ([NodeOSC](https://github.com/maybites/NodeOSC)). AddRoutes has been idle since 2024 ([slashv/AddRoutes](https://github.com/slashv/AddRoutes)) |
| MIDI | MidiController 0.1.7 or SimpleMIDI 0.1.14 | Both are on the Extensions platform with macOS ARM64 builds and state 5.1 support ([MidiController](https://extensions.blender.org/add-ons/midicontroller/versions/), [SimpleMIDI](https://extensions.blender.org/add-ons/simplemidi/versions/)). Their source was not reviewed |
| Art-Net / sACN | BlenderDMX 2.3.1 from GitHub | Applies DMX in a **24 Hz timer** ([dmx.py](https://github.com/open-stage/blender-dmx/blob/main/dmx.py)). The Extensions platform still lists 2.2.4, which lacks the `SO_REUSEPORT` fix needed to share port 6454 with QLC+ on the same Mac ([v2.3.1](https://github.com/open-stage/blender-dmx/releases/tag/v2.3.1)) |
| Ableton Link | aalink 0.2.3 (cp313 arm64 wheel) | Exposes readable `beat` and `phase` properties but needs an asyncio loop object ([aalink](https://github.com/artfwo/aalink/blob/master/src/aalink.cpp)). No Blender wrapper exists, and it is untested inside Blender |
| Video out | TextureSharing v9.1.1 (Syphon Metal, NDI, OMT) | Fixed "Blender 5.2 texture readback corruption" in v9.0.3. Output is 8-bit SDR ([TextureSharing](https://github.com/maybites/TextureSharing/releases)) |

The custom OSC route wins on measured behaviour. In local tests on 5.2.3 (recorded in the project's earlier live-control note), a timer returning `0.0` ran at about **170 to 175 ticks/s idle and 94 to 118 ticks/s** when each tick requested a redraw. A non-blocking UDP socket drained in that timer received 1,352 of 1,360 datagrams at about 750 msg/s ([timers API](https://docs.blender.org/api/current/bpy.app.timers.html)). The official Lab MCP add-on uses the same polled-socket design ([Lab MCP server](https://projects.blender.org/lab/blender_mcp/src/branch/main/addon/blender_mcp_addon/mcp_to_blender_server.py)). That tick rate beats BlenderDMX's fixed 24 Hz, which drops every other frame of QLC+ Full mode at 50 Hz ([QLC+ Art-Net](https://docs.qlcplus.org/v4/plugins/art-net)). Routing a console through QLC+ OSC output doesn't help either, because it sends one 8-bit float datagram per changed channel ([oscpacketizer.cpp](https://github.com/mcallegari/qlcplus/blob/master/plugins/osc/oscpacketizer.cpp)), so a 16-bit value arrives as two non-atomic halves. Lighting consoles are better routed through the VJ host, which then sends Blender clean OSC scalars, cues and beat phase. Blender has no native tempo sync, so the host should own the clock.

The timer has to do three things in order, or nothing visible happens. Writing a custom property from Python sets no depsgraph tag, so developers "will need to manually 'update_tag'" ([rna_access.cc](https://projects.blender.org/blender/blender/src/branch/blender-v5.2-release/source/blender/makesrna/intern/rna_access.cc)). Local measurement showed that `update_tag()` re-evaluated drivers but gave **0 draws/s** until `area.tag_redraw()` was added on the 3D views ([timers API](https://docs.blender.org/api/current/bpy.app.timers.html)). Blender 5.2 also moved Geometry Nodes modifier inputs to `modifier.properties.inputs.Socket_N.value`. These inputs have no update callbacks either ([5.2 Python API notes](https://developer.blender.org/docs/release_notes/5.2/python_api/)), and the old `mod["Socket_1"]` idiom now raises a `TypeError`, as a local probe confirmed. So the loop drains the latest value per address, writes the control properties, tags the owning datablock, and then tags the views for redraw. The redraw then triggers the Syphon capture, which keeps input and output in lockstep.

Output cost is dominated by the second render, not by the copy. TextureSharing captures inside a viewport draw handler, renders the camera again with `GPUOffScreen.draw_view3d`, reads the pixels to the CPU and uploads them into a Metal texture ([operators.py](https://github.com/maybites/TextureSharing/blob/master/operators.py)). `GPUTexture` exposes no native handle, so zero-copy sharing is impossible from Python. Headless capture after `gpu.init()`, new in 5.2 ([5.2 Python API notes](https://developer.blender.org/docs/release_notes/5.2/python_api/)), measured **11.4 ms at 720p, 24.0 ms at 1080p and 44.5 ms at 4K** for the default cube, with pure readback taking only 1.6 ms at 1080p. Real scenes cost more, and UI mode pays for the visible viewport as well. Plan for 1080p30, or render at 720p and let the host upscale. Two caveats change the operating mode. First, Syphon only sends a frame when the viewport redraws, and the steady-stream option covers NDI and OMT only ([README](https://github.com/maybites/TextureSharing/blob/master/README.md)). An idle scene therefore goes dark unless the timer keeps tagging redraws. Second, headless mode might be faster, but whether Syphon discovery notifications get delivered without a pumped run loop is unverified. That leaves one visible Blender window, overlays off, as the proven mode. VDMX users confirm the V9 Syphon path works with Blender 5 ([VIDVOX forum](https://discourse.vidvox.net/t/texture-sharing-add-on-v9-0-0-for-blender-5-x-upwards/8924)).

## Show reliability is built outside Blender, because Blender has no show mode

Scene switching is a shader problem first. Enabling EEVEE Next for the first time took about 13 s, and later switches took a fraction of a second because compiled shaders are reused ([devtalk](https://devtalk.blender.org/t/blender-4-2-eevee-next-feedback/31813?page=19)). On macOS, viewport shaders depend on the system Metal cache, with no EEVEE-specific persistent cache documented. The cleanest cue model is one `.blend` file with several Scenes, switched through `window.scene` after a pre-show pass that draws each scene at show resolution. Each scene has its own depsgraph ([commit](https://projects.blender.org/archive/blender-archive/src/commit/73dc8c24e44ba8b462f88c1c629a84c98979ef41)), so it gets evaluated on first activation. Appending or linking assets mid-show is the worst option, because it adds file I/O and new materials that compile on first draw. An in-Blender scene switch is a hard cut. Crossfades belong in the host, between two Syphon sources, which means either two Blender instances (with GPU contention on one M1 Max) or Blender plus a pre-rendered clip.

The preferences that matter live in a separate show profile. Set Texture Time Out and VBO Time Out to 0 so GPU assets stay resident ([Manual, System prefs](https://docs.blender.org/manual/en/latest/editors/preferences/system.html)). Turn Auto Save off, since it writes a backup on a timer ([Manual, Save & Load](https://docs.blender.org/manual/en/latest/editors/preferences/save_load.html)), and keep undo low. Script auto-execution is off by default ([Manual, Save & Load](https://docs.blender.org/manual/en/latest/editors/preferences/save_load.html)). Simple Expression and AVERAGE/SUM drivers skip the Python interpreter and run anyway ([Drivers manual](https://docs.blender.org/manual/en/latest/animation/drivers/drivers_panel.html)), so live parameters should use those driver types and never scripted ones. Pin the Blender and add-on versions, because 5.x breaks old scripts in quiet ways. The engine id changed from `BLENDER_EEVEE_NEXT` to `BLENDER_EEVEE`, and curves now respect `resolution`, which renders default hair with about **15x more geometry** than 4.5 ([5.0 EEVEE notes](https://developer.blender.org/docs/release_notes/5.0/eevee/)). Metal-specific shader failures, such as magenta world shaders and PSO creation errors, have their own tracker history ([Issue #112952](https://projects.blender.org/blender/blender/issues/112952), [Issue #116414](https://projects.blender.org/blender/blender/issues/116414)). Validate the show file on the exact build you'll run.

Recovery has to assume Blender will eventually vanish. The host should treat the Blender Syphon source as optional and fall back to a pre-rendered clip of the same scene. It should then relaunch Blender with the show file and a warm-up script, budgeting tens of seconds for shader compilation before the layer is usable again. This is inferred design. No source reports crash rates for multi-hour Rendered-viewport sessions on Metal, and none measures App Nap or occlusion throttling of a background Blender window. Both need a full-length rehearsal on the target machine.

## Agents build good scenes from a template, small scripts and screenshots

Two MCP servers matter, and they do different jobs. The official Blender Lab MCP requires Blender 5.1+, bundles the Python API and manual for 5.2 with search tools, and provides headless `*_for_cli` twins, window and area screenshots, and renders to a path ([readme_tools.rst](https://projects.blender.org/lab/blender_mcp/raw/branch/main/readme_tools.rst), [readme.md](https://projects.blender.org/lab/blender_mcp/raw/branch/main/readme.md)). The community "MCP for Blender" server adds Poly Haven, Poly Pizza, Sketchfab and four 3D generators. Its `look` tool returns multi-angle sheets and animation frame strips in one call ([README](https://github.com/ahujasid/mcp-for-blender/blob/main/README.md)). Neither has dedicated tools for materials, Geometry Nodes or animation, both route almost everything through code execution, and neither authenticates its localhost socket. The Lab server has known sharp edges. Thumbnails can render at full scene resolution (#70, #61), the socket fails silently when Online Access is off (#45), and the `.mcpb` bundle fails to install on macOS (#57) ([issues](https://projects.blender.org/api/v1/repos/lab/blender_mcp/issues?state=open&type=issues&limit=50)). The best split is Lab MCP for authoring and verification against 5.2, and the community server only during an asset-gathering phase, with telemetry off.

The practitioner evidence agrees on what makes agent-built scenes good. One developer who built a multi-agent Blender system called a viewport screenshot after every operation the "single biggest quality improvement", and found that splitting "decide" from "write bpy" helped ([devtalk](https://devtalk.blender.org/t/built-a-multi-agent-system-on-top-of-blenders-python-api-and-sharing-architecture-learnings-for-the-mcp-discussion/44260)). Exposing 50+ narrow tools made results worse, because the model "spent more tokens deciding which tool to call", and one general code tool performed better ([issue #4](https://projects.blender.org/api/v1/repos/lab/blender_mcp/issues/4)). The Lab connection prompt says to inspect before assuming, return structured dicts, capture references right after creation because names auto-suffix, and prefer modifiers over destructive edits ([prompts.yml](https://projects.blender.org/lab/blender_mcp/raw/branch/main/mcp/blmcp/data/prompts.yml)). Each call starts with a fresh namespace and needs its own `import bpy` ([issue #55](https://projects.blender.org/api/v1/repos/lab/blender_mcp/issues/55)). Context is the hidden cost. One `get_objects_summary` on a 1,670-object scene returned about **904 KB and added about 15.5k tokens** to the next request ([issue #54](https://projects.blender.org/api/v1/repos/lab/blender_mcp/issues/54)).

Agent limits line up with the risky parts of a VJ scene. A hands-on test with Claude Code found that iterative modeling and material fixes worked, but on Geometry Nodes "the second something breaks inside one it already built, it kind of flounders" ([MakeUseOf](https://www.makeuseof.com/claude-code-loose-in-blender-is-a-completely-different-assistant-than-it-is-in-a-cad-program/)). A secondary review reports the same pattern: node graphs get brittle beyond a few nodes, complex procedural shaders and animation curves are weak, and lighting gets placed without any judgment of whether it looks right ([MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance)). A Blender developer sees MCP's value in diagnosis, naming, shading fixes and validation more than in generating whole scenes ([devtalk](https://devtalk.blender.org/t/built-a-multi-agent-system-on-top-of-blenders-python-api-and-sharing-architecture-learnings-for-the-mcp-discussion/44260)). Stale training data adds a predictable failure on 5.2, because the GN modifier input path changed.

These findings point to a concrete authoring workflow. Start from a template with fixed collections and one control datablock (a Scene or an Empty) that holds every live parameter as a custom property with UI ranges. A local 5.2.3 probe confirmed that an AVERAGE driver from `scene["svj_amp"]` onto `modifiers["GN"].properties.inputs.Socket_1.value` evaluates correctly. The agent writes idempotent `build_scene.py` functions kept in git rather than one-off console edits. It assembles Geometry Nodes logic from several small node groups with named, exposed inputs, and it expresses motion as drivers bound to control properties instead of hand-keyed F-curves, which also makes the result controllable live. For complex graphs, a human or a downloaded asset supplies the hand-tuned node tree, and NodeToPython, which added 5.2 support in its 2026 release, converts it into code the agent can read and edit ([NodeToPython](https://extensions.blender.org/add-ons/node-to-python/)). A project skill should list the 5.2 paths that were verified to work. Rich-Siomporas, who forked the Lab MCP with a skills registry, reports that skills "can dramatically improve performance" on well-defined tasks ([issue #39](https://projects.blender.org/api/v1/repos/lab/blender_mcp/issues/39)). For assets, Poly Haven is CC0 and needs no key. Poly Pizza models are about 69% CC-BY and come with attribution properties ([README](https://github.com/ahujasid/mcp-for-blender/blob/main/README.md)). Hunyuan3D's licence excludes the EU, UK and South Korea ([HF LICENSE](https://huggingface.co/tencent/Hunyuan3D-2/blob/main/LICENSE)). Generated meshes also need decimating before they are usable in EEVEE. At show time, stop MCP entirely. Its calls run on Blender's main thread and would compete with the output loop.

## Conclusion

The research points to one shared design rule for both questions. The scene's **control surface** is the real product, not the scene itself. A single control datablock with a few ranged custom properties, fanned out through non-Python drivers, is what makes a scene cheap to drive live, safe with script auto-run off, immune to recompile hitches, and easy for an agent to build and verify. Agents are weakest at free-form node graphs and keyframed timing, and live shows punish exactly those, so constraining the agent to the template makes it more reliable and the show more stable.

The open risks are empirical, not architectural, and a rehearsal on the target machine can close all of them. Nobody has measured real-scene EEVEE frame rates on Apple Silicon, whether 5.2 fixed the 5.1 warm-cache regression, end-to-end latency from OSC input to Syphon output, multi-hour stability on Metal, or headless Syphon discovery. Until those numbers exist, the honest position is a hybrid. Run a few warmed, parameterized Blender hero scenes as optional Syphon layers, keep a pre-rendered clip behind each one, and leave clock, audio analysis, crossfades and console input to the host.
